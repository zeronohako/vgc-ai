# vgc-ai

## Goal
A dashboard that analyzes a Pokémon VGC position (4 active Pokémon) and shows the best moves, plus which 4 to bring and 2 to lead, for a player in a live game: ranked battles, Global Challenges and similar. **Not** a ladder bot. Background research: `vgc-bot-research-summary.md`.

**Closed team sheets (CTS) first.** Those games run on CTS: the player knows their own team; of the foe only the six species at preview and whatever has been revealed. The system should support both CTS and OTS eventually; for now everything targets CTS (format `gen9championsvgc2026regmc`). OTS-only pieces stay as options: `selfplay.py --ots`, and `analyze.py`/`check_positions.py`, which still read full-information OTS replays (M-B).

**Direction (2026-11-05): Reg M-C, mikumiku37's design.** A policy/value network trained by PPO self-play in Ninjask (no human games, only a team pool), with the one-turn matrix search + regret matching we already have at play time; the network's value replaces the hand-written score at the leaves. Build order: M-C team pool → self-play environment (Ninjask 0.4's `Batch`) → network + PPO → network in the search → bring/lead → UI. The heuristic stays as the baseline the network must beat; progress is measured **bot vs bot**, agreement with human replays is only a weak signal.

**Where things stand:** the network (`runs/cpu-v1`, 1 CPU hour) beats random ~98% but scores only ~40% against the hand-written 1-ply search in the arena, and an extra 30 min of CPU training didn't move that measurably (it did beat its own 30-min self 56%). **Next:** the first GPU run on Kaggle with `kaggle/train.ipynb` (GPU support done 2026-11-06 and smoke-tested on a Kaggle T4; the notebook clones the repo from GitHub, so **push main first**: pushing from this shell fails, GitHub refuses both SSH keys without the user's passphrase, so the user pushes), then PFSP (part of each iteration's games against past snapshots instead of the current net); see next steps 4-5.

`analyze.py` assumes full information (it rebuilds positions from OTS logs, foe sets included). A CTS analysis needs the foe's hidden sets sampled (next steps).
Pipeline: replay log → position at start of `<turn>` in Ninjask → every joint action for both sides → each pair played with N seeds → feature vector per cell → score = `F @ WEIGHTS` → regret matching → ranked moves + opponent's likely plays. `--depth 2` re-values a top-k cut by the one-turn game of each resulting position (below).

**Evaluator** (`FEATURES`/`WEIGHTS` in `analyze.py`, my side minus foe): hp (per mon 0.5 alive + 0.5·HP fraction; ±10 for a win) 1.0, Tailwind turns left 0.15, boost stages 0.08 (all stats equal), screens (Reflect + Light Screen turns, Veil = both) 0, protect (Protect-type moves chosen this turn) 0, status per mon slp/frz −0.3, par/brn/tox −0.15, psn −0.1. Ignores Trick Room (in 78/324 M-B games), Encore/Perish/redirection value. Weight tuning is done (coordinate search kept these weights; a flat Protect penalty only hurts). Not worth more hand-tuning now: the network replaces it.

**Agreement with humans** (`check_positions.py`: 40 random positions, seed 0, plus 3 dev; "worse" = share of our options ranked strictly above the human's, 0 = our top pick, 0.5 = random; players are mostly unrated Bo3 ladder players). 1-ply on the 43 positions (86 decisions): fresh 0.247 (human = our top pick 10/80, top 10% 31/80), dev 0.130 (1/6, 4/6). The earlier 0.245/78 lacked two positions the old switch match skipped.

**2-ply search** (`search2`, `--depth 2`; built and verified, not tuned, parked by the direction change). The full one-turn matrix picks the top-k actions per side (EV vs the opponent's mix, plus anything its equilibrium plays ≥1%); each cut cell is played with `--seeds2` seeds and each resulting position is valued by its own full one-turn matrix (1 seed per cell, seeds offset from the root's) solved by LP; fainted mons are replaced first as a small simultaneous game; a win is ±10. `deepen` spreads children over processes. Dev position, k 8 × 8 × 4 seeds = 256 children: 11 s on 12 workers; all 43 positions: 12.6 min. **No gain in agreement:** fresh 0.251 vs 0.247 for 1-ply (top pick 4/80 vs 10/80, top 10% 29/80 vs 31/80), dev 0.147 vs 0.130. Inside the cut (41/86 decisions with the human's action in it) the human's mean rank is 2.91 vs 2.56 for 1-ply (2-ply better 16, worse 22) and its equilibrium probability 0.165 vs 0.238 (uniform 0.122). Untested: whether it plays *stronger* (a bot-vs-bot question). Weak spots: 1 seed per child cell makes child values noisy and biased, leaves are still the one-turn heuristic, pivot switch-ins take the first legal option.

### What we learned
- **Position loading:** `Tracker.world()` works on spectator logs, but the tracker's *own* side is garbage without requests (HP as %, wrong stats). Workaround in `load_position`: build each side from the *other* player's view (where it's the foe), merge the two projections, `Battle.from_projection`. The 4 brought Pokémon come from the whole log via the `{"brought": [idx]}` assumption. Spreads are hidden in OTS; Ninjask's default guess is used. `Battle.from_projection(dx, b.projection(), 0)` reproduces `b` exactly (0/3931 cells differ), which is how search workers get the position.
- **Lost state on load:** the projection drops the `stall` volatile, so `stall_streaks` rebuilds it from the log (`{"counter": 3**n, "duration": 1}`); without it a repeat Protect always works.
- **Speed (~60 µs per simulated cell):** `copy + reseed + choose×2` with logging ≈ 25 µs; `request` + `json.loads` ≈ 70 µs per side and `projection()` + `json.loads` ≈ 400 µs, so neither is called per cell. Everything scored is rebuilt from the turn's omniscient log, which has exact HP: HP/status (`apply_hp_log`; even Regenerator's heal is logged, as `-heal ... [silent]`), boosts (`apply_boost_log`), side conditions (`turn_conds`: root counted down, `-sidestart` sets Tailwind 3 / screens 4 turns left, `-sideend` sets 0, so natural expiry is free; only Light Clay screens and Court Change read the projection). All three checked against the engine in `test_analyze.py`. A C-level `startswith` prefix filter before splitting lines halves the parsing cost. Dev position 61×55×16 seeds: 16.1 s → 3.2 s. Game values by LP (`game_value`, scipy HiGHS: ~5 ms for 60×55, vs ~140 ms for 5000 regret-matching iterations).
- **Pivot moves:** U-turn/Volt Switch/Parting Shot pause the turn for a switch-in; `finish_turn` answers with the first legal switch-in so cells are scored after upkeep.
- **Illegal actions:** `joint_choices` lists switches even when trapped (Shadow Tag etc.). `payoff_matrix` drops rows/columns rejected everywhere before mixed cells.
- **Ninjask 0.4.0 has the self-play loop built in**, which removes most of the planned Rust work: `ninjask.Batch(dex, n)` keeps both players' trackers in Rust and steps all battles on all cores with the GIL released; `observe()` returns every pending decision as numpy-ready bytes (`who` battle/side, `preview`, `obs` float32 × `OBS_LEN` 250, `ids` int16 × `IDS_LEN` 84 for embeddings sized by `Dex.vocab()` = species 391, moves 512, items 168, abilities 226; legal `actions` int8 × `ACTION_WIDTH` 8 per row with `offsets`), `step(indices)` applies one choice per decision; `reset_many` refills finished slots. Also `Battle.legal_choices/legal_actions/choose_index` and experimental exact chance enumeration (`enumerate_outcomes`, could replace seed sampling in our cells). Measured here with a random policy, 256 battles, team preview included: **5,677 games/s, 163k decisions/s** (observe 44%, step 37% of the time). mikumiku37's collection ran ~100k steps/s *with* network inference, so the network, not the simulator, is the bottleneck now; write Rust only if profiling the PPO loop says so.
- **`Batch` plays closed team sheets, even in the OTS format** (right for CTS, our target): `reset` never calls `show_team_sheets`, so a player sees only the foe's species (0/36 foe item/ability/move ids known at preview), and `Batch.battle(i)` returns a copy, so it can't be opened from Python. CTS random play: 6,217 games/s on the pool. A slot that was never reset, or whose battle ended, counts as done and `observe()` skips it (so the arena leaves finished slots idle). For OTS, `SelfPlay(open_sheets=True)` fills them in: each side's own view is complete (all six mons at preview, the four brought after it), so it keeps a per-battle sheet `[battle, side, species id] -> (item, ability, moves)`, refreshed at every decision of that side (Mega formes), and fills the foe's unknown item/ability plus the sheet's four moves by species (unique per team). Mons are *not* index-aligned across the two views (the foe's view lists all six previewed in preview order, a side's own view only its four brought), hence species. Check: where both players decide at once, the filled foe block equals the foe's own view (191,516 mons, 0 mismatches; partly true by construction, since the same call refreshes the sheet, so it mainly checks the indexing). With the fill (and the check on): 4,901 random games/s, p1 wins 50.1%, median 9 turns. Cleaner later: a `show_team_sheets` option in `Batch.reset` upstream.
- **What 0.4's observation leaves out** (`src/encode.rs`, per mon: HP fraction, fainted, seen, active, status, 7 boosts, Mega; per side 6 condition *flags*; weather, terrain, Trick Room, Gravity *flags*; ids: species, item, ability, 4 moves): turns left of Tailwind/Trick Room/screens/weather, volatiles (Protect streak, Encore, Taunt, Substitute, Perish count, Choice lock, Fake Out available), stats/spreads (embeddings must learn them from ids), and, worst, **which slot an active mon is in**: actions target foe *slots* 1/2, and "switch N" means *request* position N, while the own view keeps the brought order (93% of decisions differ). So the policy couldn't tell what it targets or switches to.
- **`selfplay.PublicState` fills those gaps from each battle's log** (public lines only; `Decisions.slots`, `.pos2own`, `.mon_x`, `.glob_x`): slot a/b per mon, request position → own mon, turns since each side/field condition started, per slot turns on the field, Protect streak, Substitute/Encore/Taunt/Perish/Leech Seed/Disable/Yawn/confusion/Heal Block/Throat Chop. The request order comes from the *submitted choices* (every "switch N" swaps two positions, as the engine does), plus drags and Ally Switch from the log; the log's switch lines would be wrong under Illusion. Foe slots come from the log, i.e. what the player sees: a Zoroark looks like its disguise. Matching is by **base species** (unique per team by Species Clause; keyed by name, since Floette-Eternal/-Mega's base Floette isn't in the dex), which survives Mega Evolution and Aegislash's formes. A failed Revival Blessing used to swallow the next forced switch: the revive flag now clears at upkeep. `test_selfplay.py` checks request order, own slots, move order, foe slots, switch targets and counters against the engine's requests: 0 errors in ~156k checks. Cost: env ~15k decisions/s instead of ~160k (`Batch.battle(i)` copies ~10-26 µs and log parsing); a Rust port is the fix when the GPU makes it the bottleneck.
- **Model (`model.py`)**: 13 tokens per decision (6 own + 6 foe mons: species/item/ability/move embeddings, observation floats, the extras above; 1 global token), a pre-norm transformer, value = tanh head on the global token, policy = one logit per legal joint action built from the tokens each slot's option refers to (actor, move, target or incoming mon), split so each distinct slot option and mon is computed once (joint rows reuse them). d 64 × 2 layers: 166k parameters; d 128 × 3: 635k. CPU forward ~230 µs per decision at d 128. Threads: torch on 6 threads with `OMP_WAIT_POLICY=PASSIVE` (train.py sets it) is best; spinning OpenMP threads fight the engine's rayon pool otherwise.
- **PPO (`train.py`)**: one network plays both sides of 256 battles; 32 env steps per iteration (~15k decisions), 3 epochs, minibatch 2048, clip 0.2, entropy 0.01, γ 0.995, λ 0.95; reward ±1 at the end only; refused choices are dropped; trajectories cut at the iteration end bootstrap with 0 advantage. Eval: 256 games against a uniformly random player (the net is p1 in even battles, p2 in odd). Snapshots `snap_<it>.pt` every `--snapshot-every` 10 iterations (net only, CPU tensors, ~0.7 MB at d 64, ~2.5 MB at d 128 × 3), for the arena and later PFSP. Log fields per iteration include `collect_s`, `train_s` and `per_s` (decisions/s over the iteration). **GPU (2026-11-06):** `--device` (default cuda if available) trains there, the env stays on the CPU; `--act-device` picks rollout moves on another device (a CPU copy of the net, `load_state_dict` after every update) in case small GPU calls are slow; `model.py` creates every tensor on its inputs' device; checkpoints load with `map_location`. `--runs-dir` and `--resume-from DIR` (copies ckpt/log/snapshots in when the run has no checkpoint) are for Kaggle's input/output folders. **On a Kaggle T4 (2026-11-06 smoke run, d 128 × 3 = 635,203 parameters, 64 battles):** works; ~3,400-3,700 decisions/s (collect 0.5-0.6 s + train 0.5 s per ~3,600-decision iteration), vs ~1,170/s for the d 64 × 2 net on this PC's CPU with the same settings; vs random 44% untrained → ~90-97% within 0.4 min (32-game evals). Notebook benchmark (256 battles, ~15k decisions per iteration): **moves picked on the GPU 4,312 decisions/s** (collect 1.3 s + train 2.1 s per iteration) vs 2,263/s with a CPU copy of the net (collect 4.2 s), so `--act-device` stays cuda; ~4.5× this PC's ~950/s with a 4× bigger net, ~100M decisions in a 7 h session (cpu-v1 saw 3.4M). Training is now the larger share: mixed precision (T4 tensor cores) or the idle second T4 are the next speedups, not needed yet. Kaggle's Python was ≥ 3.12 (`/usr/bin/python3`, so no uv fallback) and `pip install ninjask==0.4.0` worked with its torch. Checked on CPU: fresh run, resume into a new folder (continues at the next iteration, log and snapshots carried over), and the separate-actor branch (`--act-device cpu:0`, which torch treats as a different device: KL stayed ~0.001, so the copy is synced); the code parses as Python 3.12. CPU: ~650-960 decisions/s overall (collect ~5-7k/s, train ~2.3-3.8k/s per epoch).
- **First run, `runs/cpu-v1` (2026-11-05, CPU, d 64 × 2 layers, 30 min):** 120 iterations, 1.72M decisions, 98.5k games. Win rate against a random player (256 games each): untrained 55.8% → 86.8% at 3 min → 92.6% at 6 min → ~97% from 12 min on (96-99%, 96.9% at the end). Policy entropy 3.6 → 0.97 nats; KL ~0.01, clip fraction ~0.11; value loss flat ~0.38-0.41 (self-play between equals is close to a coin flip). It learns, and random is now saturated as a yardstick: the next measure has to be a real opponent. Resumed for another 30 min (iterations 120 → 239, 59 min in all, ~3.4M decisions): vs random still 96-99%, entropy ~0.92.
- **Arena (`arena.py`, 2026-11-05):** each pool team pairing is played twice, same teams on the same sides, players swapped; score = A's points (win 1, draw 0.5), 95% interval over pairings. `SelfPlay(matchups=...)` plays a fixed game list. Players: `random`, a network (sees what the player sees, samples its policy; `--greedy` for argmax), `search` = `analyze.py`'s 1-ply search on the *real* battle (knows the foe's hidden sets; 4 seeds per cell, regret-matching mix sampled; forced switches valued by the next turn's one-turn game via `position_value`; random team preview; skips ally-targeted moves). Its choice strings index `Battle.legal_choices(side)`, whose `legal_actions` match `Batch`'s rows exactly (8,465/8,465 decisions); `legal_choices` = `joint_choices` in the same order plus ally-target options (-1/-2) in between, so every `joint_choices` string is in it (at team preview `joint_choices` gives `['']`, `legal_choices` the 90 `team ABCD` picks). A decision the search can't answer falls back to a random choice and is counted (0 in the 400 games vs search). A refused choice is never resubmitted (random among the rest), so a greedy net can't loop. 12 workers, 1 engine + 1 torch thread each (`RAYON_NUM_THREADS=1`, `torch.set_num_threads(1)`), one task per pairing (an env of 2 battles). Search ~2.1-2.5 s per decision on 12 workers (1.26 s alone: the 6 cores are hyperthreaded): 200 games vs search ~7-8 min; net vs net 400 games ~12 s. Output: A's score ± 95%, as p1 / as p2, pairings A won both / split / lost both, median turns (5 net vs random or net, 7-8 vs search), ms per decision of each player; every match is appended to `runs/arena.jsonl`.   So the search (with full information and ~500× the thinking time: ~2.1-2.5 s vs ~5 ms per decision) is the bar, and a CPU hour of training hasn't closed the gap; the net still gains on its own past self, slowly. 200 games resolve only ±7%: telling a few points apart vs search needs ~1,000 games (~40 min) or fewer seeds.
